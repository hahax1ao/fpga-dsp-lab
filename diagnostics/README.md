## 实际执行流程

1. 用户选择任务及交互方式后，才将其改为 active并更新 CURRENT。默认独立练习，其他方式为提示、详细讲解、代码评审。
2. 优先记录不查资料的首次判断；不确定可直接说明。查阅资料或接受提示后补充时保留初稿，记录来源、帮助程度与修改原因，不要求闭卷考核。
3. 用户独立制作交付物。Agent 不生成当前任务的完整答案、RTL、TB、算法实现或预制结果；可按请求解释局部概念、审查和排错。
4. 用户提交后进入 review。Agent 检查任务标准，区分用户自述、已查看文件、实际运行与板测等证据；没运行的项目标未核验。自动化脚本仍需单独授权。
5. 按领域给出已掌握点、薄弱点、证据限制和少量下一项建议；依据 WORKFLOW，经用户确认后更新能力画像和验收记录。证据检查后仍保持 review，只有用户认可才能标记 done，记录认可位置。诊断结束不表示每道题都答对或所有能力都达到 L2。

## 统一验收与评级

- 每项必须有实际交付、关键设计或推导解释、所用资料/提示记录和可追溯成果位置。错误回答是有效诊断证据，环境失败不自动判 L0。
- 实作区分“功能检查通过”“环境受阻”“仍需补强”。功能未通过时保留失败证据，足以识别问题后可完成诊断记录；若仍无法区分环境与能力原因，保持 blocked 或 review。
- 仿真能力不能替代 STA/CDC 能力，简单定点模型不能证明复杂通信算法能力，静态设计不能证明上板能力。
- L0–L3 按 SKILLS 的定义逐领域评估；首次短题和单个简单实验通常不足以证明 L3。没有被覆盖的能力保留未评估，已有工程可在用户愿意分享时补充证据以避免重复训练。

## 成果与恢复

当前每项只有 README。用户开始后按需要在同一任务目录保存回答、手写代码、模型、约束及结果，不预建空子目录。暂停记录最后完成步骤、错误/波形或模型现象、工具版本和下一项具体操作。原始结果保留，新一轮结果另存；不覆盖用户文件。
